## 从一个慢查询说起

500 万用户的系统里，一条登录查询跑了 3 秒。DBA 检查发现表上没有任何索引——不是忘了建，而是列序不对。

1 亿订单的场景更典型：查某用户最近 20 笔订单，索引顺序差一列，执行计划从走索引退化成全表扫描。

这不是缺索引，而是索引设计方法的问题。

## 01 · 唯一字段用唯一索引

用户表 500 万行数据，核心查询有三条：按用户名登录、按手机号登录、按状态分页。用户名和手机号在业务上具有唯一性，应该建唯一索引而非普通索引：

```sql
CREATE UNIQUE INDEX uk_sys_user_username ON sys_user(username);
CREATE UNIQUE INDEX uk_sys_user_phone ON sys_user(phone);
```

订单表 1 亿行数据，按订单号精确查询同理：

```sql
CREATE UNIQUE INDEX uk_orders_order_no ON orders(order_no);
```

唯一索引同时解决两个问题：查询走索引、业务层防重复。

> **设计原则** 用唯一约束替代应用层判重，由数据库保证数据一致性。

预约系统更典型——一个用户同一天同一个时间段只能预约一次，业务规则直接固化到表结构：

```sql
CREATE UNIQUE INDEX uk_visitor_reservation_user_date_slot
ON visitor_reservation(visitor_id, schedule_date, time_slot_id);
```

数据库层约束比代码层加锁更可靠，没有判重窗口期。

| 场景 | 数据量 | 索引 | 类型 |
| --- | --- | --- | --- |
| 用户名登录 | 500 万 | `uk_sys_user_username` | 唯一索引 |
| 手机号登录 | 500 万 | `uk_sys_user_phone` | 唯一索引 |
| 订单号查询 | 1 亿 | `uk_orders_order_no` | 唯一索引 |
| 防重复预约 | — | `uk_visitor_reservation_user_date_slot` | 唯一联合索引 |

## 02 · 过滤加排序靠联合索引

用户表第三条查询——按状态分页：

```sql
SELECT * FROM sys_user WHERE status=1 ORDER BY create_time DESC LIMIT 20;
```

这条查询同时涉及过滤和排序，单列索引无法覆盖两个操作。建联合索引：

```sql
CREATE INDEX idx_sys_user_status_create_time ON sys_user(status, create_time);
```

订单表同理，查某用户最近 20 笔订单：

```sql
SELECT * FROM orders WHERE user_id=10001 ORDER BY create_time DESC LIMIT 20;
```

```sql
CREATE INDEX idx_orders_user_create_time ON orders(user_id, create_time);
```

先按 user_id 等值过滤，再按 create_time 排序，索引列序与查询路径一致。

商品表查询更进一步，三个条件叠加：

```sql
SELECT * FROM product WHERE category_id=10 AND status=1 ORDER BY create_time DESC;
```

```sql
CREATE INDEX idx_product_category_status_create_time
ON product(category_id, status, create_time);
```

> **设计原则** 等值在前，范围在后，排序收尾。范围查询之后的列无法有效利用索引，把范围列放前面会拖垮后续字段的命中率。

反例对照——同一条查询 `WHERE user_id=? AND status=? AND create_time>?`：

| 索引设计 | 列序 | 命中情况 |
| --- | --- | --- |
| ✓ 推荐 | `(user_id, status, create_time)` | 等值 + 等值 + 范围，三列全部命中 |
| ✗ 不推荐 | `(create_time, user_id, status)` | 范围在最前，后续两列利用率趋近于零 |

```sql
-- 推荐：等值在前，范围在后
CREATE INDEX idx_orders_user_status_create_time ON orders(user_id, status, create_time);

-- 不推荐：范围查询排在最前
CREATE INDEX idx_orders_wrong ON orders(create_time, user_id, status);
```

## 03 · 覆盖索引减少回表

当查询只需要索引中包含的列时，数据库可以直接从索引返回结果，跳过回表步骤。

以用户表为例：

```sql
SELECT * FROM sys_user WHERE phone='13800138000';
```

这条查询先走 phone 索引找到主键，再回表取完整行数据，两次 IO。如果业务只需要 id 和 phone 两列：

```sql
SELECT id, phone FROM sys_user WHERE phone='13800138000';
```

phone 索引的叶子节点本身就存了 phone 值和主键 id，查询所需的列全部在索引里，无需回表。

> **优化收益** 覆盖索引把两次 IO 压缩成一次。设计阶段考虑查询列与索引列的匹配，能减少大量回表开销。

## 04 · 三个常见的索引设计错误

### 错误一：给所有字段建索引

一张表 10 个字段建 8 个索引，每条 INSERT 维护 8 棵 B+ 树，写入性能骤降。

### 错误二：在低区分度字段上建单列索引

status 字段只有 0 和 1 两个值，索引区分度极低，优化器大概率选择全表扫描而非走索引。这类字段只适合作为联合索引的组成部分，不宜单独建索引。

### 错误三：联合索引列序与查询不匹配

查询条件是 `WHERE user_id=? ORDER BY create_time`，索引却建成 `(status, create_time, user_id)`。status 不在查询条件里，user_id 排在最后，最左前缀匹配失效。

| 错误 | 后果 |
| --- | --- |
| 所有字段建索引 | 空间浪费，写入性能骤降 |
| 低区分度字段建单列索引 | 优化器不走索引，等于白建 |
| 联合索引列序不匹配 | 最左前缀匹配失效，无法充分利用索引 |

## 设计四步法

1. **收集核心 SQL**：整理 WHERE、JOIN、ORDER BY、GROUP BY 条件
2. **分析查询模式**：识别高频查询、过滤与排序的组合
3. **设计联合索引**：等值在前，范围在后，排序收尾
4. **EXPLAIN 验证**：用执行计划确认索引真正命中

> **核心结论** 匹配业务访问路径，是索引设计的唯一目标；不是堆砌索引数量。
